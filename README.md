# 🛒 Commerce Payment System

## 1. 프로젝트

### 프로젝트명
**Commerce Payment System**

### 팀명
**5마에와 모 신데이로**

### 프로젝트 소개

상품 조회부터 회원가입, 로그인, 장바구니, 주문, 결제 및 주문 취소까지의  
**커머스 결제 시스템을 구현한 팀 프로젝트**입니다.

주문 생성 시 상품 재고를 차감하고, 결제 성공/실패에 따라 주문 및 결제 상태를 변경하며,  
결제 실패 또는 주문 취소 시 재고를 복구하도록 구현했습니다.

또한 도메인별 책임을 분리하고 **Facade와 Command Service를 활용하여 서비스의 책임을 분리**했습니다.

## 3. 주요 기능

### 👤 회원 / 인증

- 회원가입
- 로그인
- Access Token 발급
- 로그인한 사용자의 내 정보 조회
- 비밀번호 BCrypt 암호화 저장
- 이메일 중복 검증

### 🛍️ 상품

- 상품 전체 목록 조회
- 카테고리 / 가격 범위 필터링
- 페이지네이션
- 최신순 정렬
- 상품 단건 조회
- 품절 상품 조회 시 품절 상태 확인

### 🛒 장바구니

- 로그인한 사용자의 장바구니 조회
- 상품 장바구니 담기
- 동일 상품 추가 시 수량 증가
- 장바구니 상품 수량 변경
- 장바구니 상품 개별 삭제
- 장바구니 전체 비우기

### 📦 주문

- 주문 미리보기
- 장바구니 상품을 기반으로 주문 생성
- 주문 생성 시 재고 차감
- 주문 목록 조회
- 주문 상세 조회
- 주문 취소
- 주문 취소 시 재고 복구

### 💳 결제

- 결제 승인 요청
- 결제 성공 / 실패 처리
- 결제 성공 시 주문 완료 처리
- 결제 성공 시 장바구니 비우기
- 결제 실패 시 주문 취소
- 결제 실패 시 차감된 재고 복구
- 주문별 결제 정보 조회

> 현재 프로젝트에서는 실제 PG사 결제 연동 대신 **모의 결제 방식**으로 결제 성공/실패 흐름을 구현했습니다.

## 4. 시스템 구조

프로젝트는 도메인별로 책임을 분리하여 구성했습니다.

```text
Controller
    ↓
Service / Facade
    ↓
Repository
    ↓
Database
```

### 주요 도메인

- Member
- Product
- Cart
- CartItem
- Order
- OrderItem
- Payment

주문 과정에서 여러 도메인의 기능이 함께 필요한 경우
`OrderFacade`를 통해 각 도메인의 Service를 조합하도록 구성했습니다.

## 7. 프로젝트 회고

이번 프로젝트를 통해 단순히 기능을 구현하는 것뿐만 아니라,
**도메인별 책임과 객체 간의 의존 관계를 어떻게 설계할 것인지** 고민해볼 수 있었습니다.

특히 주문과 결제 과정에서 여러 도메인의 상태가 함께 변경되기 때문에
트랜잭션과 데이터 정합성이 중요하다는 것을 직접 경험했습니다.

프로젝트 초기에 하나의 Service에 여러 도메인의 책임이 집중되었던 구조를
`OrderFacade`를 도입하여 개선하면서,
각 객체가 자신의 책임에 집중하도록 역할을 분리하는 것의 중요성을 배웠습니다.

또한 `PaymentCommandService`를 구현하면서
결제 성공과 실패에 따른 주문 상태, 결제 상태, 재고 및 장바구니의 상태가
서로 연결되어 있다는 것을 이해할 수 있었습니다.

이번 프로젝트를 통해 코드가 정상적으로 동작하는 것뿐만 아니라
**유지보수하기 좋은 구조와 데이터의 정합성을 함께 고려해야 한다는 점**을 배울 수 있었습니다.
